## 总结

Option C 是把 Option B 的"问答助手"（**B-① 电影目录语义检索 + B-② 文档 RAG**）升级成**真正的 agent 平台**：新增**持久向量库**（pgvector 或 qdrant 二选一，需直面 Docker Desktop 仅 3.826 GiB 内存的取舍）、扩展**电影语料**（外部简介导入，涉及获取与版权合规）、加**推荐系统**（协同过滤 + LLM 重排）、加**agent tools**（查电影 / 查订单 / 购物车操作 / 员工写操作**需人工审批**）、**多轮对话**、**审计日志**、**预算/配额**，并把评测集**分层进 CI**（确定性单测阻塞、夜间真实调用不阻塞）。它完整覆盖 README roadmap 第 4 项的 authorization / human approval for writes / budgets / audit logs / observability，是简历价值最高的版本。**但也是风险最高的版本**：涉及安全边界变化（写操作 + 审批 + 可能的 JWT 独立 trust boundary，**必须另立 issue + oracle 审查**，AD-1）、数据合规（外部语料）、基础设施内存（向量库容器与 LLM 争 3.826 GiB）、以及"复杂度爆炸"。本机数据的现实也要正视：`sales` 仅 **13,556** 行、`customers` **454** 行、`ratings` 仅 **8,005** 行（覆盖 21,087 部电影的一部分）→ **协同过滤严重数据不足**，推荐更适合做"内容特征 + LLM 重排"而不是经典 CF。**如果时间有限，优先做下面 30%**：① 向量库持久化（或先把 `SimpleVectorStore` 做到可重建）、② 一个**只读** tool（查电影）+ 一个**写** tool（购物车加购）走"提议→人工批准→执行"、③ 审计日志 + 预算硬上限、④ 评测集接入 CI（分层）。这四件就能把 roadmap 第 4 项的核心叙事讲完；推荐系统与外部语料都可延后。

### 1.3 数据现实对 G3（推荐）的影响（诚实评估）

- **`ratings` 仅 8,005 行**（21,087 部电影的一部分有评分），**`sales` 13,556 行**、**`customers` 454 行** → 用户-物品矩阵极度稀疏，**经典协同过滤（CF）难以得到可用质量**（冷启动严重）。
- 更现实的路径（**建议**）：
  1. **内容特征排序**（genres / stars / year / director / rating）作为候选集与基线；
  2. **LLM 重排**：把候选（少量）与用户历史（购物车/购买）作为上下文，让模型排序并解释理由；
  3. **可选**：用 LLM **合成/补全**特征（如从简介抽取标签）提升候选质量。
- 结论：G3 应表述为"**推荐候选 + LLM 重排 + 可解释性**"，而**不是**"搭建工业级 CF 系统"；任何声称 CF 有高离线指标的表述都缺乏数据支撑（**未实测、数据不足**）。

## 4. 方案设计（草案）

### 4.1 C-1 向量库：pgvector 还是 qdrant（含内存取舍）

| 选项 | 优点 | 缺点 | 与 3.826 GiB Docker 的关系 |
| --- | --- | --- | --- |
| **pgvector（Postgres）** | 与 Spring AI 官方 starter；SQL 生态熟悉；可承载元数据查询 | 需同步数据/备份策略；**占用分两块（P2-15）**：① **镜像体积 = 数百 MB**（磁盘，与 8 GiB 内存墙无关）；② **运行内存 = 数百 MB（含连接/缓存，待实测）** | 与 mysql + app + (未来) 其他容器**争内存**；**可能需调大 Docker 内存配额**（用户可控，但**挤的是宿主 8 GiB**） |
| **qdrant** | 向量原生、轻量（Rust）、Docker 镜像可小；Spring AI starter | 又一个独立服务/存储；无 SQL 生态；**镜像小 ≠ 运行内存小**（运行内存待实测） | 同样受 Docker 内存约束 |
| **宿主机原生**（Postgres/qdrant 装在 macOS 上，非 Docker） | 绕开 Docker 内存墙；与本机 Ollama 同理 | 偏离"可复现的 Compose"约定（scout §D18 强调 Compose 可复现性）；Windows/Linux 协作环境需另配 | **内存来自 8 GiB 统一内存**（仍紧张，但不与 Docker 竞争） |
| **继续 `SimpleVectorStore`** | 零依赖 | 重启即失、不能多实例 | 无额外内存 |

**docs-writer 建议**：

1. **首选 pgvector**（Spring AI starter + SQL 生态 + 与既有 MySQL 并存的心智更简单）；
2. 但**先解决 Docker 内存**：`docker info` 显示 3.826 GiB 是 **Docker Desktop 的设置**，可调大（用户可控，**属环境变更，需用户决定**）；若不调大，则在**宿主机原生**跑向量库（与 Ollama 同理）；
3. **无论选哪个，都要有"索引重建"能力**（§4.2），因为语料会变、库可能被清空；
4. 若最终仍受内存限制 → **降级方案**：`SimpleVectorStore` + **磁盘持久化快照**（把 `documents` 存文件，启动时重载），可满足"跨重启"，但不能多实例。

```
来源（**未获批准：D-C3 未裁定**）→ 原始简介文本
   │ ① 合规评审：许可/条款/是否可再分发（必须先做）
   │ ② 清洗：去 HTML/广告/乱码、语言检测、长度裁剪、去重、与 movies.id 对齐（标题+年份匹配）
   │ ③ 不入仓库（默认）：存数据库/对象存储，仓库只放"导入脚本 + 校验规则"（避免版权与体积问题）
   ▼ 文档化：来源、版本、条数、覆盖率、失败样本
```

| 关键问题 | 处理建议 |
| --- | --- |
| 语料可否提交进仓库 | **默认不提交**（版权与体积）；仓库只放脚本与规则 |
| 与 `movies.id` 对齐 | 用 title+year 匹配；**必须报告匹配率与未匹配样例**；匹配失败的电影在 RAG 中标注"无语料" |
| 语料质量 | 对生成回答的**引用正确性**影响最大 → 语料进评测集 |
| 多语言 | 若简介为英文、用户问中文 → 需要跨语言检索（embedding 模型的多语言能力**待实测**） |

### 4.3 C-3 推荐（内容特征 + LLM 重排）

```
输入：用户历史（购物车/购买/session 内浏览）
  ▼ 候选生成（确定性、可测试）：genres/stars/director/year/rating 规则 → 候选 N（如 50）
  ▼ 召回过滤：排除已购/已在购物车；按业务规则过滤（可测试）
  ▼ LLM 重排：候选（含结构化字段 + 可选简介片段）+ 用户画像 → 排序 + 每条理由
输出：top-k 推荐 + 理由 + 来源（可解释）
```

| 设计点 | 建议 |
| --- | --- |
| 是否做 CF | **不做**（数据不足，§1.3）；如用户坚持，需先明确"离线指标不可信"的预期 |
| 可测试性 | 候选生成与过滤**必须**是确定性纯逻辑（可单测、覆盖率高）；LLM 重排 mock |
| 评测 | 离线：候选命中率/多样性/新颖性（**定义需明确**）；在线无（无真实用户） |
| 与现有 UI 集成 | 首页或 movie detail 的"为你推荐"区块（沿用既有页面模式与缓存约定，契约文档 §4） |

### 4.4 C-4/C-5 Agent tools 与写操作审批（**安全核心**）

**工具清单（草案）**：

| 工具 | 类别 | 现有能力 | 审批 |
| --- | --- | --- | --- |
| `searchMovies(criteria)` | 只读 | 复用 `SearchService`/`MovieListRepository` | 不需要 |
| `movieDetails(movieId)` | 只读 | 复用 movie detail 查询 | 不需要 |
| `myCart()` | 只读（本人） | 复用 `CartService.getCart` | 不需要 |
| `myOrders()` | 只读（本人） | 复用 `sales` 查询（**注意：无 price 列**，#30 证据） | 不需要 |
| `addToCart(movieId, qty)` | **写** | `CartService.updateCart`（add/increase） | **需要人工批准** |
| `removeFromCart(movieId)` | **写** | `updateCart`（delete/decrease） | **需要人工批准** |
| `addStar(name, birthYear)` | **写（员工）** | `EmployeeController.addStar` 的 service 层 | **需要人工批准 + 员工身份** |
| `addMovie(...)` | **写（员工）** | `EmployeeController.addMovie` | **需要人工批准 + 员工身份** |
| 支付/结账 | **排除** | — | **不暴露**（不可逆 + 敏感） |

**授权模型（草案）**：

1. **身份来源**：沿用现有 session 身份（`AuthenticatedCustomer`、`EmployeeIdentity`）；**工具执行前在每个调用点做权限校验**（不依赖 prompt/模型自律）。
2. **最小权限**：顾客工具只能访问**本人**数据（cart/orders）；员工工具要求 `employee` 会话属性。
3. **只读/写分离**：写工具**必须**走审批；审批 = 把"具体动作 + 参数 + 影响摘要"返回给用户（UI 展示），用户确认后**由服务端执行**（不是模型执行）。
4. **AD-1 边界**：网页端仍是 session 认证；**是否引入 JWT/Spring Security 作为 agent 平台独立 trust boundary 必须另立 issue + 计划 + oracle 审查**（契约文档 §10）。**本方案不预设结论**：可能结论是"沿用 session 即可"（因为 agent 与网页同源同信任域），也可能是"若未来把 agent 暴露给外部客户端，则需要独立 token 机制"。
5. **CSRF**：现状无 CSRF 保护（契约文档 §9）；新增写端点会**继承**该残余风险 → 必须在风险中记录；是否引入 CSRF **属单独决策**。

**审批流（草案）**：

```
用户："把《X》加入购物车"
  ▼ 模型选择 tool + 参数（addToCart(movieId=X, qty=1)）
  ▼ 服务端校验权限 + 参数 + 预算
  ▼ 生成 pending 审批记录（id、工具、参数、影响摘要、过期时间）
  HTTP 200 { status:"success", action:"approval_required", approval:{id, summary, expiresAt} }
  ▼ UI 展示确认按钮（role="alert"/"status"、可测）
  ▼ POST /api/boot/ai/approvals/{id}/approve
  ▼ 服务端再次校验（session 身份 + 未过期 + 未重放）→ 执行 tool → 写审计
  HTTP 200 { status:"success", result:{...} }
```

| 安全要求 | 说明 |
| --- | --- |
| 审批不可被模型伪造 | 模型只能"提议"，**批准来自用户 HTTP 请求**，服务端校验身份 |
| 幂等/重放 | 审批 id 一次性；**语义对齐 `docs/plans/issue-30-migrate-cart-payment-confirmation-flows.md` §7.4 的 T1 语义**（token 一次性、**重放优先于空车**、过期失败），便于 review 对照；**但不复用其实现**（P2-16） |
| 参数白名单 | 工具参数严格校验（movieId 存在、qty 范围） |
| 影响摘要 | 中文/英文摘要由服务端生成（不让模型自定义文案） |
| 过期 | 审批记录有 TTL；过期即失败 |
| 审计 | 提议、批准、执行、失败都记录 |

### 4.5 C-6 多轮对话

- 存储：**首版建议服务端 session**（符合 AD-2 单实例）或**请求级无状态**（前端携带历史）。**注意**：session 属性须 `Serializable`（契约文档 §9）。
- 上下文压缩：历史消息 + 检索片段总长受 8 GiB 模型上下文限制 → 需要明确的截断/摘要策略（**参数待实测**）。
- **与 AD-2 的耦合**：换多实例前，会话记忆与审批状态都会失效 → 必须记录为约束。

### 4.6 C-7 审计日志

| 字段 | 示例 |
| --- | --- |
| 时间 | ISO-8601 |
| 身份 | `customer:<email>` / `employee:<email>` / `anonymous`（**避免记录密码/卡号**） |
| 请求 | 会话/请求 id、端点、输入长度（**不记录完整敏感文本**） |
| 工具 | 工具名、参数摘要（数值/ID）、结果（成功/失败/拒绝） |
| 审批 | 审批 id、批准人、批准时间、过期 |
| 模型 | 模型名/版本、延迟、token 估算 |
| 检索 | 命中文档数、来源列表（不记录全文） |

存储形态：**追加式记录**（文件/表）；**保留期仍待用户确认**。**其中"是否记录用户问题原文"已单列为决策项 D-C7（P2-17）**：**用户已于 2026-10-19 决定：默认不记录原文**（只记长度/哈希），保留期仍待定。

### 4.7 C-8 预算/配额

| 维度 | 建议上限（**除外部 API 日限外，数值仍待用户给数**） | 超限行为 |
| --- | --- | --- |
| 每会话请求数/小时 | 待定 | 明确失败（`{status:"fail"}` 或 429，**需定稿**） |
| 单次请求 token 估算上限 | 待定（依据模型上下文） | 截断或拒绝 |
| 并发 LLM 调用 | **1**（本机单实例模型，估算） | 排队或拒绝 |
| 工具调用次数/请求 | 待定（如 ≤5） | 强制停止 |
| 外部 API 兜底（若启用） | 每日 token/金额硬上限：**✅ 已确认（用户，2026-10-19）= 默认关闭；启用时 $2/日 且 ≤200k tokens（可调）**（同总览 D7） | 自动关闭兜底并明确告知 |

### 4.8 C-9 可观测性（端到端）

沿用 Option B 的指标，并加：工具调用次数/成功率、审批等待时长与批准率、检索命中、预算剩余、外部兜底启用次数。**注意**：roadmap 明确要求 "end-to-end observability"，因此指标必须覆盖"用户请求 → 检索 → 模型 → 工具 → 审批 → 执行"的全链路。

### 4.9 C-10 评测进 CI（分层）

| 层 | 内容 | 阻塞 PR |
| --- | --- | --- |
| 确定性单测 | 纯逻辑（候选生成、过滤、参数校验、权限校验、审批状态机、来源提取） | **是** |
| 契约/集成 | 端点 + filter + 审批流（mock 模型） | **是** |
| 前端 | 页面/流程 + a11y | **是** |
| e2e | UI 流程（API 全 mock，含"审批按钮"路径） | **是** |
| 夜间评测 | golden set（含工具选择正确率、审批正确性、推荐可解释性） | **否** |

**新增 golden set 维度（相对 Option B）**：① **工具选择正确率**（该调用哪个工具）；② **参数正确率**；③ **该审批而未审批的漏检率（必须为 0）**；④ 越权尝试（问别人的订单）→ 必须拒绝。

### 4.10 被否决的候选

| 候选 | 否决理由 |
| --- | --- |
| 让模型自行决定执行写操作 | 安全红线（roadmap 明确要求 human approval） |
| 暴露真实支付/结账为 tool | 不可逆 + 敏感 + roadmap 未要求 |

| 大规模 CF 训练 | 数据不足（§1.3） |
| 抓取外部语料直接入库 | 合规红线 |

| 多实例扩展 | 违反 AD-2；需单独重新评估 |

## 7. 风险与回退

| 风险 | 概率 | 影响 | 缓解 / 回退 |
| --- | --- | --- | --- |
| **安全边界变化**（写操作、审批、可能的 JWT） | 中高 | 高（高风险项） | **必须先立 AD-1 边界 issue + oracle 审查**；实现"服务端校验 + 审批 + 审计"三层；**暂停并问用户** |

| **推荐数据不足** | 高（数据事实） | 中 | 不做 CF；用内容特征 + LLM 重排；**如实报告**离线指标不可信 |
| **复杂度爆炸/工期超限** | 高 | 中 | 严格按 §5.2 的 30% 优先级裁剪；每个 C-x 独立 issue/验收 |
| **审批流被绕过** | 中 | 高 | 服务端强制（不依赖模型）；评测含"越权/漏审批"用例；代码审查 |
| **审计泄露隐私** | 低中 | 中高 | 字段白名单；不记录敏感值与完整原文；保留期策略 |
| **成本失控**（若启用外部兜底） | 中 | 中 | 预算硬上限 + 自动关闭兜底 + 可观测 |
| **多实例需求出现**（违反 AD-2） | 中 | 中 | 记录约束；出现即重新评估 AD-2 并更新 `docs/architecture/` |
| **CSRF 残余风险**（新增写端点） | 中 | 中 | 记录为残余风险；是否引入 CSRF 单独决策 |

### 7.1 回退方案

1. **逐阶段回退**：C-x 各自独立；未合并即 revert。
2. **功能开关**：`fabflix.ai.tools.enabled`（只读）、`fabflix.ai.write-tools.enabled`（写，**默认关闭**）、`fabflix.ai.external-fallback.enabled`（外部兜底，默认关闭）。
3. **向量库回退**：持久库 → `SimpleVectorStore`（功能降级但可用）。
