## 1. 数据来源与字段

### 1.1 来源表（唯一数据来源）

| 字段 | 来源 | SQL 形状（现有代码可复用） |
| --- | --- | --- |
| `id` | `movies.id`（**不透明 `VARCHAR(10)` 主键**；只有 **9,073/21,087** 以 `tt` 开头，其余如 `AWw10`/`AA1`） | `MovieDetailRepository.MOVIE_SQL` |
| `title` | `movies.title` | 同上 |
| `year` | `movies.year` | 同上 |
| `director` | `movies.director` | 同上 |
| `genres[]` | `genres.name` ⨝ `genres_in_movies` | `MovieListRepository` 的 `GROUP_CONCAT` 写法 |
| `stars[]`（top-3） | `stars.name` ⨝ `stars_in_movies` | `ROW_NUMBER() OVER (PARTITION BY movie_id ORDER BY star_movie_count DESC, name)` + `WHERE star_rank <= 3`（同 `MovieListRepository:120-200`） |
| `rating` | `ratings.rating`（`LEFT JOIN`，可缺） | `MovieListRepository` / `MovieDetailRepository` |
| `vote_count` | `ratings.vote_count` | 可选，**首版卡片不包含**（见 §2.3） |

**`rating` 的类型陷阱（实测，卡片必须归一到一种形态）**：同一个 `rating` 字段在现有两个端点上**类型不一致** —— 列表接口（`MovieSummary.movie_rating`）是 **`Float` 且可空**，详情接口（`MovieDetail.movie_rating`）是 **`String`**。因此：

- 卡片契约固定为 **`rating: number | null`**（单精度浮点语义，0–10，保留一位小数）；**任何**后续实现（工具返回值、卡片文本、embedding 文档）都必须先归一，不得直接透传两套类型。
- `null` 与 `0` 严格区分：`null` = 无评分行（当前快照 **13,082/21,087** 部；**196–2000 的 11,975 部全部无评分**，评分自 **2001** 年起才有行）；**不得**用 `0`、空串或“未知”以外的方式填充。

**不存在**的字段：`synopsis` / `plot` / `description` / 影评 / 获奖 / 票房 / 时长 / 语言 / 国家 / 海报 URL。`createtable.sql:5-10` 只有 `movies(id,title,year,director)` + `ratings`，scout §B.3 已核实。**这是全部可用文本**，也是“不能做剧情问答”的根因。

## 2. 卡片模板（`movie-card/v1`）

### 2.1 模板定义

| 模板 ID | 用途 | 字面模板 |
| --- | --- | --- |
| `en-short` | embedding 文档（低成本）、工具返回后的一行摘要 | `{title} ({year}) directed by {director}. Genres: {genres}. Rating: {rating}.` |
| `zh-full` | embedding 文档（默认，信息最全）、推荐理由的字段来源 | `电影《{title}》（{year}）导演 {director}；类型：{genres}；主演：{stars}（前 3）；评分 {rating}/10。` |
| `pipe-full` | 调试/评测对照（已批准方案 §4.2 的字面模板） | `{title} ({year}) \| director: {director} \| genres: {genres} \| stars: {stars} \| rating: {rating}` |
| `card-object` | **工具返回值**（结构体，非文本） | `{id, title, year, director, genres[], stars[]（≤3）, rating}` |

规则：

- `{rating}` 缺失 → `en-short` 写 `Rating: N/A`；`zh-full` 写 `评分 暂无`。**不得**填 0 或省略字段（省略会让模型以为该片评分低）。
- `{genres}` **全量拼接、不截断**：当前快照 **全量平均 1.2061 个/片（有 genre 的片内 1.4313）、最多 4 个**，且 **3,318 部一个 genre 都没有** → **0 genre 时** `en-short` / `pipe-full` 写 `Genres: N/A`，`zh-full` 写 `类型：暂无`；**不得跳过该字段**（跳过会让模型误读为“没有类型信息”）。**4 genre 必须完整输出**，不得按“最多 3”截断或校验。
- `{stars}` **固定前 3**（沿用现有 top-3 排序语义，可复现）；当前快照 **3,352 部没有任何主演行** → 该情形必须给**显式占位符**（不得留空串）；具体写法与是否并入 `null_placeholder` 见 §9 `MC-U8`。
- 同一片的 `zh-full` 与 `card-object` **必须由同一次 SQL 结果生成**，不得两套口径。
- 模板文本中**不含** `id`（`zh-full`/`en-short`）：目录主键对语义检索无贡献、且会让模型误当可引用事实。`card-object` 含 `id`，因为工具调用/引用需要。

### 2.2 Token 与成本估算

**实测（B1.5a 报告 `docs/ai/reports/b1-5a-embedding-eval.md`，2026-11-09；21,087 卡全量 × 2 模板 × 2 模型）**。tokens 因 tokenizer 而异，必须按模型分列：`zh-full` **47.2**（`bge-m3`）/ **50.7**（`qwen3-embedding:0.6b`），`en-short` **26.8** / **29.1**。卡片字符长度：`zh-full` min 43 / median 107 / max 192，`en-short` min 53 / median 77 / max 149。两个候选**同为 1024 维**，向量占用与模型无关。

| 组合（**实测**，batch=32，`keep_alive=30m`） | 卡片数 | tokens 合计 | tok/卡 | 构建耗时 | 向量内存（float32, 1024 维） |
| --- | --- | --- | --- | --- | --- |
| `bge-m3` × `zh-full` | 21,087 | 994,857 | 47.2 | **532.5 s ≈ 8.9 min** | 86,372,352 B ≈ **82.4 MiB** |
| `bge-m3` × `en-short` | 21,087 | 564,371 | 26.8 | **516.7 s ≈ 8.6 min** | 82.4 MiB |
| `qwen3-embedding` × `zh-full` | 21,087 | 1,068,956 | 50.7 | **397.0 s ≈ 6.6 min** | 82.4 MiB |
| `qwen3-embedding` × `en-short` | 21,087 | 613,781 | 29.1 | **315.8 s ≈ 5.3 min** | 82.4 MiB |
| **4 组合合计（串行）** | — | ≈ 3.24 M | — | **1,762 s ≈ 29.4 min** | 峰值单模型 82.4 MiB |

- 实测构建区间 **5.3–8.9 min/组合**、合计 **29.4 min**，落在计划的“理想 21–28 min / 预算 45–60 min”之内。
- **旧外推已被实测替换**（`zh-full` ≈48 / `en-short` ≈25.3 tokens；`bge-m3 × en-short` 4–5 min）：`en-short` 实测 8.6 min ≈ 旧外推的 2×，因为实际瓶颈是**卡片速率**（40.8 卡/s，batch=32）而非纯 token 速率。**对外引用成本时必须用上表实测值，不得再用 1.01 M / 3.09 M 那组外推数。**
- 稳态吞吐实测：`bge-m3` **1,873 tok/s**（旧外推区间 1,860–2,450 的下沿）、`qwen3-embedding` **2,702 tok/s**（高于旧上沿）。旧的“13× batch 离群值”**本次未复现**（batch max/p50 = 1.3× 与 2.0×）。

| 历史对照（旧 9,052 实例，**不再使用**） | tokens | 耗时 | 内存 |
| --- | --- | --- | --- |
| 9,052 × `zh-full` | ≈ 0.43 M | ≈ 3–4 min | ≈ 37 MB |
| 9,052 × `en-short` | ≈ 0.23 M | ≈ 2 min | ≈ 37 MB |

> **输入上限（已实测，不再是开放项）**：`bge-m3` 的真实上限是 **2,048 tokens**（`prompt_eval_count` 在 902 → 1,802 → 2,048 后不再增长；`/api/tags` 声明的 `context_length=8192` **不可信**），`qwen3-embedding:0.6b` 是 **4,095 tokens**（而非 32,768）。单卡最长 50.7 tokens，距两个阈值都有 ≈40× 余量，B1.5a 的 659 batch × 4 组合**静默截断次数 = 0**。本文**仍然不允许**首版把多片拼进一个 embedding 文档——一旦合并，2,048 上限会真实生效且**不报错**。

### 2.3 字段取舍

| 字段 | 进 embedding 文档 | 进工具返回值 | 理由 |
| --- | --- | --- | --- |
| `title` | ✅ | ✅ | 片名检索/消歧必需 |
| `year` | ✅ | ✅ | 年代筛选与“同年代”相似性 |
| `director` | ✅ | ✅ | 作者性相似（“喜欢诺兰”） |
| `genres[]` | ✅ | ✅ | **最强相似信号**（全量平均 1.2061 个、最多 4 个，区分度有限但可靠；**3,318 部为空**） |
| `stars[]`（top-3） | ✅ | ✅ | 演员相似（“还有他演的片吗”） |
| `rating` | ✅ | ✅ | 质量门槛；**不是相似性信号**（同分不等于相似） |
| `vote_count` | ❌ v1 | ❌ v1 | 口径未定（是否加权/展示），加进来会改变卡片 fingerprint |
| `id` | ❌ | ✅ | 文本里无检索价值，但工具/引用必需 |
| 剧情/影评/获奖 | ❌ | ❌ | **数据不存在** |

## 3. 卡片能支持什么、不能支持什么

| 能力 | 支持度 | 依据 | 说明 |
| --- | --- | --- | --- |
| 按片名找片 | ✅ | `title` 字段 | 精确/部分匹配；工具路线可用普通 SQL/LIKE，不必上向量 |
| 按类型筛选 | ✅ | `genres`（当前快照 **56 个 distinct 名称 / 61 行**） | 值域可枚举，但含重复行与长尾名称 → 必须 DB 派生 + 规范化 |
| 按年份区间筛选 | ✅ | `year` **196–2024** | 数据集已定（D-3）；超出覆盖 → `OUT_OF_RANGE` + `coverage` |
| 按评分筛选 | ✅ 但受限 | `rating`（**13,082** 部缺，且**只覆盖 2001+**） | 缺失必须显示“暂无评分”；**旧年代 + 评分条件不可满足**（`EMPTY_RESULT` + `coverage`） |
| “有没有类似《X》的电影” | ⚠️ **有限** | 共享 `genres`/同年代/同导演/同主演 | 能给出**可解释**的相似；不能给出“风格/气质/主题”相似 |
| 按偏好推荐（类型/年代/导演/演员/评分） | ✅ | 上述字段 | 属**内容特征**推荐，不是协同过滤 |
| 解释推荐理由 | ✅ 但只能基于字段 | 同上 | 理由 = 字段交集；不得生成剧情/主题理由 |
| 按主演找片 | ✅ | `stars_in_movies` + top-3 | 只覆盖前 3 主演（`star_rank <= 3`） |
| **剧情/简介问答** | ❌ | 无 `synopsis` 字段 | 必须拒绝（`ai-user-workflows.md` U6） |
| **主题/情绪/风格/“烧脑”** | ❌ | 无对应字段 | 词表里没有，不能假装有 |
| **获奖/票房/时长/语言/地区/海报** | ❌ | 无字段 | 拒绝 |
| **个性化“根据我的历史”** | ❌ | `ratings` 仅 8,005 行（**只覆 2001+**）、无用户-电影评分表映射到查询用户 | 不得声称个性化 |
| **跨语言片名翻译** | ⚠️ 不支持 | 只有英文原名 | 用户用中文片名（如“黑客帝国”）时**无法**直接命中；需用户给英文名或接受失败（B1.5 需实测这一点） |

> **“中文片名”是候选 A 的一个真实风险点**：卡片里只有英文原片名，`bge-m3` 即使多语言，也**不一定**把“黑客帝国”映射到 `The Matrix`（需要模型具备影片知识或片名翻译对齐）。B1.5 的 `zh→en` 用例必须包含这类“中文常用译名 → 英文片名”的样本，并如实记录失败率；**不得**用“用户会输入英文名”来回避。

### 3.1 “相似 / 推荐”的信号白名单（不得超越）

| 允许的信号 | 不允许的（数据不存在或不可验证） |
| --- | --- |
| 共享 `genres`（枚举精确匹配；全量平均 1.2061 个/片、最多 4 个、3,318 部为空） | 剧情/主题/情绪/风格相似（无 `synopsis`，也无任何文本字段） |
| `year` 接近或同年代 | “看过这部的人还喜欢……”（`ratings` 只有 8,005 行且只覆盖 2001+，无面向查询用户的评分映射） |
| 同 `director` | 奖项/票房/时长/语言/地区/海报 |
| 共享 `stars`（限前 3 主演） | 外部站点评分或口碑 |
| `rating` 区间（**仅作品质门槛，不是相似性信号**） | “口碑/评分趋势”类结论（无时间序列） |

> **对外表述硬约束**：可以写“类型/年代/导演/主演相近”，**不得**写“剧情相似”“风格类似”“充满张力”等一切依赖不存在字段的描述；也**不得**承诺“与你喜欢的电影相似”（无用户历史）。这条约束对两种用法（embedding 文案与工具 `similarity_reason`）**同等适用**。

## 4. 两种用法：embedding 文档 vs 工具返回值

| 维度 | 用法 ①：卡片作为 **embedding 文档** | 用法 ②：卡片作为 **MCP/工具返回值** |
| --- | --- | --- |
| 目的 | 语义相似检索（“类似《X》”“2005 年后的高分剧情片”） | 结构化筛选/相似/推荐，由 LLM 组织答案 |
| 数据流 | 卡片文本 → `bge-m3` → 向量 → top-k | LLM → 工具调用 → 卡片结构体 → 答案 |
| 新鲜度 | 需**重建索引**（新片/改模板/换模型都要重建） | **实时**查询 DB，天然最新 |
| 一次性成本 | 21,087 卡 ≈ 1.01 M tokens（`zh-full`）/ 0.53 M（`en-short`）；两模型两模板 ≈ 3.09 M | **0**（无离线构建） |
| 查询成本 | 1 次 embedding（B1.5a 实测热态 p50 **35–59 ms**、冷启动 **1.37–2.37 s**） | 1 次 chat（56–70 tok/s）+ 工具查询（待实测） |
| 可解释性 | 弱：相似度分数不可解释，需另造理由 | 强：`similarity_reason` 来自字段交集 |
| 失败模式 | 静默截断、模型换入换出、索引陈旧 | 工具选错、槽位错、chat 幻觉（需强制 grounding） |
| 语言 | 依赖 embedding 跨语言能力（头号风险） | 不依赖（槽位是结构化的） |
| CI 可测性 | 需要真实 endpoint（PR CI 无 LAN，`AC-B-8`） | 工具层可纯单测（mock DB）；LLM 路由部分需真实调用 |
| 认证/权限 | 索引是内存/DB 数据副本，需与现有登录边界一致 | 直接复用现有认证过滤器与只读查询 |
| 是否需“语料” | **是**（卡片文本即语料） | **否**（无语料，只有查询接口） |

**允许混合（B1.5 待评估）**：工具内部用向量做“相似”（`find_similar_movies` 的实现可选 embedding 或字段加权），但**对 LLM 暴露的仍是工具契约**。混合不改变本文的卡片契约。

## 5. 数据新鲜度与重建策略

| 触发 | 必须做什么 | 谁负责 |
| --- | --- | --- |
| 电影数据导入/更新（新片、改标题、补评分） | 若走 embedding 路线：重建受影响片的向量（首版允许**全量重建**，因为 10–20 min 成本可接受）；工具路线无需动作 | 实施方 |
| 卡片模板变更（字面文本、字段顺序、缺失值写法） | **必须** bump `card_version` + 重建索引 + 更新本文 §2 | 实施方 + `docs-writer` |
| embedding 模型/维度变更 | 重建索引 + 更新 fingerprint | 实施方 |
| 数据集切换（如重新导入或换实例） | 重建 + 重算 `db_snapshot_hash` + 更新 §1.2 与对外“覆盖范围”表述 + bump `snapshot_export_version` | 实施方 + `docs-writer` |
| 索引持久化形态变更（内存 → 持久库） | 更新本文与方案；不改变卡片字段契约 | 主 agent 裁定 |

**重建可复现性要求**：给定 (数据库快照, 卡片模板版本, 模型名+维度, 批次大小)，重建必须产生**相同的卡片文本**；向量是否逐位相同不做要求（浮点/GPU 非确定性），但 top-k 结果应稳定（同一 query 多次运行命中集合一致）。

## 7. 更新规则

1. **字段/模板/版本变更 → 必须更新本文**，并同步 `docs/architecture/ai-user-workflows.md`（工具返回的 `Movie` 对象）。
2. 每次更新：改 `last_updated`、必要时 bump `card_version`、在 §8 追加变更行、更新 §1.2 的数据口径（若规模变化）。
3. `docs-writer` 维护；reviewer 在正确性审查中核对“代码里的卡片文本 == 本文 §2.1”。
4. 本文**不包含**实现细节（类名、SQL、缓存实现）；那些属计划/代码。本文只保证**数据契约**稳定。
