## 0. 实测证据（逐项，主 agent 提供）

> 本节只记录**被实测到的事实**。凡"推算/估计"都在括号里写明；未测项列在 §0.7，不并入本节。

### 0.1 端点与环境连通性

| 项 | 结果 | 说明 |
| --- | --- | --- |
| 用户原地址 `192.68.87.48` | **不通** | 判定为笔误（`192.68.x.x` 不是常规私网段书写），不作为环境问题记录 |
| 正确地址 `192.168.87.48:11434` | **可达**（Mac 端 `curl` 正常） | Ollama 默认端口 11434；Mac 与 PC 同局域网 |
| 鉴权 | **无** | 无 token、无 TLS；请求即答 |
| 模型清单 | `qwen2.5:7b` 4.68 GB、`bge-m3` 1.16 GB | 与计划里"chat 2–6 GB + embedding 0.3–1 GB"的估算区间一致（bge-m3 略高于估算上限） |

### 0.2 GPU 占比取证（`GET /api/ps`）

| 模型 | 字段 | 值与解读 |
| --- | --- | --- |
| `qwen2.5:7b` | **`size_vram` = `size` = 4.76 GB** | **100% GPU**：整份权重都在显存里，**没有 CPU offload**（若 offload，`size_vram` 会明显小于 `size`） |
| `bge-m3` | 未单独记录 `size_vram` | **未确认**（主 agent 只回传了 qwen 的读数）→ 不推断 |

**为什么这条值得留证**：这台 PC 的实测吞吐（§0.3，56–70 tok/s）只有在**GPU 全量驻留**的前提下才成立；若换到 CPU 或部分 offload，同一模型的 tok/s 会掉一个量级。也就是说，这些数字**不能平移**到"M2 / 8 GiB 原生 Ollama"的假设上。

### 0.3 Chat 热请求（OpenAI 兼容 `POST /v1/chat/completions`，`qwen2.5:7b`）

| # | 问题 | completion tokens | 耗时 | 推算吞吐 | 回答质量 |
| --- | --- | --- | --- | --- | --- |
| 1 | "用一句话介绍《教父》" | 27 | **0.48 s** | **≈56 tok/s**（27 ÷ 0.48） | **正确** |
| 2 | "列出三部 1990 年代科幻电影…" | 218 | **3.12 s** | **≈70 tok/s**（218 ÷ 3.12） | **出现事实错误**：把 2009 年的《阿凡达》列为 90 年代作品 |
| 3 | "什么是 RAG…" | 171 | **2.50 s** | **≈68 tok/s**（171 ÷ 2.50） | **合理**（概念性解释，与通行定义一致） |

**读法**：

- **速度**：热请求下 **56–70 tok/s**，长回答（218 tokens）也在 3 秒级 → 非流式首版（计划 §4.3「首版不支持流式」）在演示层面可接受。
- **质量**：概念题（#1/#3）可用；**事实清单类问题（#2）会幻觉**。7B 模型对"具体年份/片单"这类记忆型知识不可靠 —— 这正是 **B-② 必须带检索来源（RAG）**、**B-③/B-① 必须由语料/数据库结构约束**的直接实测依据；不能依赖模型自身知识回答目录类问题。
- **口径限制**：tok/s 是**由 completion tokens ÷ 端到端耗时推算**，不是从 Ollama 响应的 `eval_count` / `eval_duration` 字段直读；含网络与调度开销，属**下界近似**。

### 0.4 Embedding（`POST /v1/embeddings`，`bge-m3`）

| 项 | 结果 |
| --- | --- |
| 向量维度 | **1024** |
| 首次（冷启动） | **7.64 s**（含模型加载） |
| 第二次 | **2.56 s**（仍处换入/预热区间） |
| 之后热请求 | **0.129 s**、**0.071 s** |
| 查询侧 embedding（该轮检索中） | **约 2.3–2.5 s** —— 与热请求 0.07–0.13 s 差一个量级，判定为**模型重载 / keep-alive 过期**导致（该轮 chat 与 embedding 交替调用，`bge-m3` 被换出后又换入） |

**读法**：

- **维度 1024** 落到计划 §4.2 的算术里：`21087 × 1024 维 × 4 B ≈ 86 MB`（**推算值，未实测**）→ 与"内存不是约束、成本是一次性 embedding 时间"的原判断一致（计划 P1-2）。
- **冷/热差异 100 倍**（7.64 s vs 0.071 s）必须在设计上处理：索引构建/首次请求要预留**模型加载时间**，`/api/boot/ai/status` 之类的"就绪"语义也应能区分"模型未加载"与"模型不可用"。
- **换入换出成本真实存在**：单机同时只驻留一个模型时，chat 与 embedding 交替调用会反复加载 → 直接威胁 `p95 延迟`（D8 里"先实测后定"的那一项）。**该 p95 目标值本次仍未定**。

### 0.5 小型中文检索实验（余弦相似度，`bge-m3`）

语料：**4 条 `docs` 风格中文 chunk**；查询：**3 条中文 query**。

| query | 是否命中该 query 最相关的 chunk | 最高余弦相似度 |
| --- | --- | --- |
| "后端测试覆盖率要求是多少？" | **是（top-1 正确）** | **0.6990** |
| "部署时用什么 JRE 镜像？" | **是（top-1 正确）** | **0.6121** |
| "Spring AI 需要什么 Java 版本？" | **是（top-1 正确）** | **0.8445** |

**读法（必须连带限制一起读）**：

- 方向**可行**：中文 query → 中文 chunk，3/3 命中 top-1，`bge-m3` 的多语言能力在本项目语料形态上**没有显示出方向性缺陷**。
- **这仍然不是质量基准**：**4 chunk / 3 query** 的样本量下，随机命中概率本身就高（1/4），**没有对照模型、没有中→英跨语言用例、没有 top-k 曲线、没有分段/长文档场景**。因此：
  - **`AC-B-12` 未满足**（计划要求"**至少 2 个**多语言候选完成中→中/中→英对比"）—— 本次只测了 **1 个候选（`bge-m3`）**，且**没有中→英**用例。
  - **D8 的"RAG 引用正确率 ≥95%"未被验证**（引用正确性需要真实回答 + 来源比对，本次只测了检索 top-1）。

### 1.3 仍存在的风险、边界限制、未验证项与后续事项

1. **样本极小，"方向可行"≠"质量达标"**：检索实验 = **4 chunk / 3 query**，随机基线本身就是 25%；`top-1` 命中不能替代 `recall@k`、不能替代引用正确性。**`AC-B-12`（≥2 候选 + 中→英）仍未满足，D8 的"引用正确率 ≥95%"与 p95 均无任何证据** → 若把本日志读成"embedding 风险已消除"就是过度声称。
2. **7B 事实性错误（已实测复现）**：《阿凡达》(2009) 被列入"1990 年代科幻片"。**缓解 = 语料/结构约束，不是换 prompt**：B-② 的答案必须来自检索到的 chunk 且带来源；B-①/B-③ 的候选集必须来自 `movies` 表，模型只做"条件解析"或"重排"。**风险不会因 B0 通过而消失**。
3. **冷启动 / 模型换入换出**：冷 7.64 s vs 热 0.071 s（**约 100×**），且 chat 与 embedding 交替调用会把 `bge-m3` 推出显存（查询侧回落到 2.3–2.5 s）。**未验证**：`keep_alive`/常驻策略、并发 1 下的真实 p95、索引构建期（21087 条）的稳态吞吐。→ **p95 目标值仍待实测后再定（D8 未闭环）**。
4. **局域网端点无鉴权（安全边界）**：`http://192.168.87.48:11434` **无 token、无 TLS**，任何能进该局域网的主机都能调用（包括消耗 GPU、读取模型、以及未来若接入的语料内容）。当前**可接受的前提**是"仅家用/实验局域网 + 不承载敏感语料"；**一旦部署到任何共享网络，必须先加鉴权/反向代理/绑定限制**（部署专项 §"不要默认暴露到局域网"的约束仍然成立）。

## 2. 新增知识点 / 重点学习对象

> 只记录本次**真正新增或显著涉及**的内容；通用 HTTP/JSON 常识不重复罗列。

### 2.1 接口与协议（Ollama 的双面 API）

| 知识点 | 含义 | 位置 | 为什么值得学 |
| --- | --- | --- | --- |
| **Ollama 同时暴露原生 API 与 OpenAI 兼容 API** | `POST /v1/chat/completions`、`POST /v1/embeddings` 走 OpenAI 形状；`GET /api/ps`、`/api/tags` 走 Ollama 原生形状。**两者共用同一进程与同一批已加载模型** | §0.3 / §0.4（兼容端点）；§0.2（原生 `/api/ps`） | 这决定了 Spring AI 的两条接入路：`spring-ai-starter-model-ollama`（原生语义、默认 `11434`）vs `spring-ai-starter-model-openai` + `base-url=http://<host>:11434/v1`（兼容语义）。**"能不能用兼容端点摸清事实"和"最终用哪个 starter"是两件事** —— B0 正是用前者在零依赖下完成了事实核对 |
| **"OpenAI 兼容"是形状兼容，不是能力等价** | 兼容端点能收发 `messages` / `input` 并返回 `usage`、`data[].embedding`；但**模型加载、显存驻留、keep-alive 这些运行时行为只能从原生端点读到** | §0.2 vs §0.3/§0.4 | 评估"是否达标"时，兼容端点给不出"是不是 GPU 在跑""模型是否被换出"；把两类端点分工（**兼容做业务、原生做取证**）是排障的基本手法 |

### 2.2 取证方法（把"感觉快"变成可核对的数字）

| 知识点 | 含义 | 位置 | 为什么值得学 |
| --- | --- | --- | --- |
| **`/api/ps` 的 `size_vram` vs `size`** | `size` = 模型占用的总字节；`size_vram` = 其中落在 **GPU/VRAM** 的部分。**`size_vram == size` ⇒ 100% GPU**；若明显小于 `size` ⇒ 有 CPU offload，吞吐会显著下降 | §0.2 | 这是区分"真的在 GPU 上跑"与"看起来能用"的唯一低成本证据。同一条 tok/s 数字，在 100% GPU 与部分 offload 下含义完全不同 —— **报数字必须带这个前提** |
| **tok/s 的两种口径：直读 vs 推算** | 直读 = Ollama 响应的 `eval_count` / `eval_duration`（模型侧纯生成速度）；推算 = `completion_tokens ÷ 端到端耗时`（含网络/调度，**下界**）。B0 用的是后者（56 / 70 / 68 tok/s） | §0.3 | 两种口径不可混用；写进报告时必须注明口径，否则"70 tok/s"会被误读成模型上限 |
| **冷/热两态必须分开测并与样本量一起报** | 同一次 spike 里，embedding 冷 7.64 s、二次 2.56 s、热 0.071–0.129 s ——**相差两个数量级**；只报"平均延迟"会掩盖模型加载成本 | §0.4 | 延迟类指标天然多峰（加载 / 首次推理 / 稳态）。**报 P50/P95 前必须先把"模型是否已加载"作为条件**，否则 p95 就是"最慢的那次加载" |
| **对照实验排除假故障**：同一目标、同一时段、换客户端 | `urllib` → `No route to host`，同时 `curl` 正常 ⇒ 问题不在网络/端点，而在**客户端权限** | §0.6 | 排障的第一原则是**改变一个变量**。这条救了 B1 一次"Spring AI 连不上 Ollama"的误判 |

### 2.3 检索概念（embedding 侧）

| 知识点 | 含义 | 位置 | 为什么值得学 |
| --- | --- | --- | --- |
| **`bge-m3` 是多语言 embedding，输出 1024 维** | 多语言（含中文）语义向量，1024 维决定了存储/计算规模：`21087 × 1024 × 4 B ≈ 86 MB`（**推算，未实测**） | §0.4 + 计划 §4.2 算术 | "维度"不是抽象参数：它同时决定**内存/磁盘**（线性）、**检索成本**（线性）与**可达精度**（通常随维度上升，但有边际递减）。选型时维度是必须落表的一列 |
| **余弦相似度阈值不可跨域套用** | 本次 top-1 分数 **0.6121 / 0.6990 / 0.8445** 分布在同一量级，但**没有"负样本最高分"作对照** → 无法据此设"低于 X 就拒答"的阈值 | §0.5 | 拒答（`should-refuse`）与"无依据时明确拒绝"（`AC-B-4`）都需要**正/负样本分数分布**才能定阈值。只看命中样本的分数是典型的**选择性取证** |
| **小样本检索实验的正确结论粒度** | 4 chunk / 3 query、3/3 top-1 正确 ⇒ 只能支撑"**方向可行、未发现多语言方向性缺陷**"，**不能**支撑"命中率 ≥80%""引用正确率 ≥95%" | §0.5 + §1.3 第 1 条 | 学会把结论**限定在样本能支撑的粒度上**：模型选型可以继续，验收数字仍必须由 golden set + 真实语料给出（计划 §6.2） |

### 2.4 模型行为与平台（约束面）

| 知识点 | 含义 | 位置 | 为什么值得学 |
| --- | --- | --- | --- |
| **7B 的"记忆型事实"不可靠 → RAG 不是装饰** | 同一模型能正确解释 RAG（概念），却把 2009 年的《阿凡达》算进 1990 年代（记忆型事实）。**概念能力 ≠ 事实检索能力** | §0.3 第 2 条 | 这是"为什么必须 RAG、必须带来源、必须在无依据时拒答"的**一手证据**；也解释了为什么 B-① 的候选集必须来自 `movies` 表而不是模型脑内 |
| **macOS 的「本地网络」权限是**按应用/可执行文件**授予的** | 系统设置 → 隐私与安全性 → **本地网络**。未授权时：某些客户端（`curl` 已授权）通，另一些（Python 解释器/未授权的终端宿主）报 `No route to host`。Java/JVM 由启动它的宿主（终端 / IDE / launchd）继承授权 | §0.6 | 这是 macOS 14+ 才系统化的隐私门槛，**与防火墙是两套机制**；不知道它就会把权限问题当网络问题查一整天 |

## 3. 结论与下一步

### 3.1 结论（实测支撑的部分）

1. **继续 Option B（本地优先）**：局域网 PC 上的 Ollama 在**全量 GPU** 前提下，chat（`qwen2.5:7b`）热请求 **56–70 tok/s**、embedding（`bge-m3`，1024 维）热请求 **0.07–0.13 s** —— 对"非流式、单用户、演示级"的 B-①/B-② 足够。
2. **默认模型定稿（B0 范围内）**：chat = **`qwen2.5:7b`**、embedding = **`bge-m3`**、向量库先用 **`SimpleVectorStore`**（沿用 D4，内存算术不受 1024 维威胁：≈86 MB 推算）。
3. **风险处置方向确认**：7B 幻觉 → **RAG + 来源 + 拒答**；冷启动/换入换出 → **懒加载 + 就绪语义 + 实测 p95 后再定目标**；局域网无鉴权 → **仅限受控局域网，跨网前必须加鉴权**。
