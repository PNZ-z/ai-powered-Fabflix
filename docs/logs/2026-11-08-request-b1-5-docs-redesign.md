### 1.2 关键设计决定（本次文档层，均标为草案）

1. **把“规范”与“语料”在物理上分开**：`ai-user-workflows.md` 是运行时指令/路由规范，显式声明禁止进入向量库；开发文档目录一律排除在用户语料之外。这样“LLM 知道怎么调用工具”不依赖检索，也不会把内部决策泄漏给用户。
2. **工具契约写成逻辑层**（name/input/output/error/limit），不绑定 MCP/HTTP/Java 形态 —— 因为 MCP 可行性尚未核实，绑定实现会让文档在核实结果出来前就过期。
3. **卡片与工具共用同一 `Movie` 对象**：`movie-cards.md` 定义字段，`ai-user-workflows.md` 的返回值直接引用它，避免两套口径。
4. **候选 A/B 用同一套 30 条金标准集**：A 看 recall@5/MRR，B 看意图/工具/槽位/接地 —— 同一输入、不同指标，才能公平比较“语义检索”与“结构化工具”。
5. **把 `AC-B-12` 的口径冲突显式上浮**（计划 §7 与 D-7）：若选 B 且不用 embedding，原条目失去对象，**不能**声称“闭合并通过”，必须由用户/oracle 裁定改写或关闭。
6. **中文片名的真实风险写进文档**：卡片只有英文原片名，`zh→zh` 实际是“中文模板 + 英文值”，“黑客帝国 → The Matrix”不一定能命中 —— 要求 B1.5 用反例集暴露它，而不是用“用户会输入英文名”回避。

## 2. 新增知识点 / 重点学习对象

### 2.1 RAG / 检索架构

| 知识点 | 含义 | 对应位置 | 为什么值得学 |
| --- | --- | --- | --- |
| **“规范文档”与“语料”的区别** | 规范是喂给模型的**指令/策略**（system prompt、tool routing），语料是**被检索的内容**。二者混用会导致模型把内部规则当事实回答，也会把开发过程泄漏给用户 | `ai-user-workflows.md` §1.1–1.2 | 这是本次方向修订的核心概念；很多 RAG 项目犯的错就是“把仓库所有 md 都塞进向量库” |
| **embedding 文档 vs 工具返回值的取舍** | 前者需要离线构建索引、有新鲜度与重建成本、相似度不可解释；后者实时查询、理由来自字段交集、但依赖模型正确选工具与填槽位 | `movie-cards.md` §4 | 这是“要不要上 RAG”的第一性问题，比“换哪个 embedding 模型”更靠前 |
| **recall@k 与 MRR** | `recall@5` = 期望结果是否出现在前 5；`MRR@10` = 第一个正确结果的排名倒数（越接近 1 越好）。多解问题（“相似电影”）必须用**可接受集合**而不是单一正确答案 | `b1-5-movie-retrieval-eval.md` §3.2 | 评测设计的核心；用单一答案会让指标虚高/虚低 |
| **grounding（接地）与可自动检验的幻觉** | “答案里的每个事实都必须来自工具返回”可以被机器检验：回查 DB 比对 title/rating 是否一致。比人工“感觉对不对”可靠得多 | 同上 §4.2（指标 4） | B0 已实测 7B 模型会编造年份；接地校验是唯一能拦住它的工程手段 |
| **fingerprint（可复现性）** | 一组能唯一标识“这次索引/评测是什么”的元数据：卡片版本、模板、数据源与行数、字段集、模型与维度、构建耗时。缺一项，数字就不可复现 | `movie-cards.md` §6 | 与仓库既有的“语料指纹”决策（D-语料指纹、`U-B8`）一致；也是评审能否相信数字的前提 |
| **静默截断** | Ollama embedding 单输入上限 2,048 tokens，超限**不报错直接截断**。它不会让程序崩，只会让检索质量无声下降 | `b1-5` §11、`movie-cards.md` §2.2 | 典型的“最难发现的 bug”：指标变差不报错 |

### 2.2 模型与工具调用

| 知识点 | 含义 | 对应位置 | 为什么值得学 |
| --- | --- | --- | --- |
| **tool calling / function calling** | 由模型输出结构化的“调用请求”（工具名 + 参数 JSON），应用执行后把结果回填给模型再生成答案。模型不直接访问数据库 | `ai-user-workflows.md` §3–§4 | 与“模型记忆回答”相比，这是把幻觉关进笼子的标准做法 |
| **`capabilities: ["completion","tools"]` 不等于“已验证可用”** | `/api/tags` 只是声明能力；真实是否能产出合法参数、能否多轮，必须实测 | `b1-5` §2.3 | “能力声明 ≠ 验证据”，与仓库既有的 `reachable ≠ ready` 是同一类思维 |
| **失败模式分类** | `no_tool_call` / `wrong_tool` / `bad_args` / `hallucinated_id` / `over_refusal` / `under_refusal` 等，比“准确率 80%”更有诊断价值 | `b1-5` §4.2（指标 8） | 知道**怎么错**才能定向修 prompt 或改工具粒度 |
| **槽位（slot）与澄清策略** | 必填/可选槽位 + “一次只问一个问题” + 多义时列候选让用户选 | `ai-user-workflows.md` R2 | 对话式检索可用性的关键；也是防止模型“猜片名”的唯一办法 |
| **冷启动与 keep-alive** | embedding 冷启动 7.64 s vs 热 0.056–0.070 s（约 100 倍），默认 5 分钟卸载 | `b1-5` §3.2、§11 | p95 延迟如果不区分“模型是否已加载”，结论就没有意义 |
