## 总结

本文回答一个问题：**在这台 Mac 上，本地大模型到底怎么跑、能跑多大、怎么接进 Spring AI**。事实基线：MacBook Pro 13" **M2**（`Mac14,7`）、**8 GiB 统一内存**、磁盘**仅 22 GiB 可用**；**Docker Desktop 只分到 3.826 GiB** 内存；本机**当前未安装**任何推理软件（`which ollama llama-cli vllm` 全空、`~/.ollama` 不存在）。由此得到三个结论：① **容器内跑 LLM 不可行** —— 不只是 3.8 GiB 内存（虽**可调大**，但会挤压宿主 8 GiB、带来换页风险），**更关键的是 macOS 上 Docker 容器无法访问 Apple GPU（无 Metal 直通）→ 容器内 Ollama 只能 CPU 推理、比原生慢一个量级**，因此必须在 macOS 上以**原生进程**运行；② 原生下现实区间是 **~3B–8B 4-bit GGUF**（8B 接近上限、上下文要小；14B+ 不现实）——**均为估算，须实测**；③ **磁盘 22 GiB** 是第二道硬约束，模型下载体积必须提前算账。方案对比推荐 **Ollama 起步**（Apple Silicon 原生、Metal 加速、`ollama pull` 一键、默认 `http://localhost:11434` 且**提供 OpenAI 兼容** `/v1/chat/completions` 与 `/v1/embeddings`），llama.cpp 作为"需要更细内存/性能控制"时的备选，LM Studio 用于人工试验，**vLLM 不推荐**（面向 CUDA，macOS/Apple Silicon 支持有限）。与 Spring AI 的对接有两条同样可行的路：专用 `spring-ai-starter-model-ollama`（默认 11434），或 `spring-ai-starter-model-openai` 把 `base-url` 指向 `http://localhost:11434/v1`（`api-key` 任意非空）。Embedding **必须选多语言模型**（候选 `bge-m3`、`multilingual-e5-*`、`qwen3-embedding` 等，**以 Ollama 实际可用性与维度为准**）——语料与提问都是中文，**embedding 的语言能力是本方案头号技术风险，必须先做中→中/中→英检索实测**（P1-1）。**性能预期必须实测**：本文给出测量方法（tokens/s、首 token 延迟、端到端延迟、内存峰值、可用上下文上限），**不填写任何虚构数字**。最后给出**本地 vs 外部 API 的决策树**与部署形态对比（本机原生 / 局域网大内存机器 / 云 GPU / Docker 的可行性边界）。**注意**：>8B 的模型或更高质量需求只能通过"更大内存机器/云 GPU/外部 API"解决，而"避免 token 成本"的目标与 8 GiB 上限之间存在客观张力（总览 §C-7）。

## 1. 本机硬件事实与结论

### 1.1 事实（scout §C11–C12，含命令证据）

| 项 | 实测值 | 命令/证据 |
| --- | --- | --- |
| 机型 | **`Mac14,7`**（MacBook Pro 13" M2, 2022） | `sysctl -n hw.model` |
| 芯片 | **Apple M2**（集成 GPU，统一内存，Metal） | `sysctl -n machdep.cpu.brand_string` |
| 内存 | **8,589,934,592 字节 = 8 GiB** | `sysctl -n hw.memsize` |
| 磁盘 | 228 GiB 总，**22 GiB 可用**，35% used | `df -h /` |
| OS | macOS 26.4、aarch64 | `mvn -version` 输出 |
| Docker Desktop | **CPUs 8，Total Memory 3.826 GiB**；Server 29.6.2 | `docker info` |
| 已装推理软件 | **无**：`which ollama llama-cli vllm` 全空；`ls /Applications` 无匹配；`~/.ollama` 不存在 | scout §C12 |

### 1.2 结论

1. **不能在 Docker 容器里跑 LLM**：容器可用内存 3.826 GiB < 7B-4bit 权重（估算 4.5–5 GB，scout §C13）；**且即便调大内存也无法用 GPU**（容器拿不到 Metal，P1-4）。
2. **必须原生运行**（Ollama.app / `llama-server`），才能使用 8 GiB 统一内存与 **Metal 加速**（容器内只能 CPU 推理，慢一个量级）。
3. **现实规模上限 ≈ 3B–8B 4-bit**（**估算**）；8B 时上下文要小、系统要留余量；14B+ 不现实。
4. **磁盘 22 GiB** 决定"能同时保留几个模型"：应把模型下载体积纳入规划（§4.2）。
5. **Docker 3.826 GiB 也约束 Option C 的向量库**（见 `ai-option-c-agent-platform.md` §4.1）。

## 3. 与 Spring AI 的对接方式

| 方式 | 依赖（**artifact 名实施时核对**） | 配置（草案） | 适用 |
| --- | --- | --- | --- |
| **A. 专用 Ollama starter** | `spring-ai-starter-model-ollama`（scout 已核实 1.1.8 存在） | 默认指向 `http://localhost:11434`；模型名/超时按 Spring AI 的 `spring.ai.ollama.*` 配置 | Spring AI 原生、配置最省心 |
| **B. OpenAI 兼容 starter 指向本地** | `spring-ai-starter-model-openai` | `spring.ai.openai.base-url=http://localhost:11434/v1`；`api-key` 任意非空（Ollama 不校验） | 想保留"切换云端"的能力（同一抽象），或需要 OpenAI 形状的高级参数 |
| **C. 裸 HTTP（无 Spring AI）** | 无（Java 11 `HttpClient`） | 自行管理超时/重试/解析 | **仅 Option 0**（零迁移 spike）；Option B 起改用 A 或 B |

**Embedding**：Ollama 提供 `/v1/embeddings`（OpenAI 兼容）与原生 embedding 接口；**必须选多语言模型（P1-1，头号风险）**：候选 **`bge-m3`**、**`multilingual-e5-*`**、**`qwen3-embedding`** 等（**以 Ollama 实际可用性与维度为准，实施时核对；维度决定向量存储体积**）。语料与提问都是中文 → **单语模型会让检索命中率系统性偏低**；**B0 spike 第一件事之一就是中→中/中→英检索对比**。embedding 通常比 chat 模型小很多（约 0.3–1 GB），适合 8 GiB。

**关键配置项（草案）**：

| 项 | 说明 |
| --- | --- |
| `base-url` | `http://localhost:11434`（native）或容器内需指向 host（**本方案不推荐容器**，见 §6） |
| `model` | chat 模型名；**固定并记录版本**（评测可比性） |
| `timeout` | **必须显式设置**；本地模型首 token 可能较慢，**具体值待实测** |
| `num_ctx` / 上下文 | Ollama 可调；小内存下**应显式限制**，**具体值待实测** |
| 并发 | 本机单实例建议**并发 = 1**（估算） |
| 流式 | 可选（Spring AI 支持 `stream`）；首版建议非流式以简化前端/测试（见 Option B §4.3） |
| 本地不可用时 | 明确失败（`{status:"fail"}`）+ 可选外部兜底开关（默认关闭） |

**注意（未确认项）**：Spring AI 1.1.x 与 Ollama 的**确切配置键名**（如 `spring.ai.ollama.chat.options.*`）需在实施时核对官方文档；本文不猜测键名。

## 4. 模型选择矩阵与磁盘预算

### 4.1 模型矩阵（**体积与内存均为估算，必须实测**）

| 规模 | 代表模型（示例，**非推荐清单的最终裁定**） | 量化 | 权重体积（估算） | 8 GiB 可用性（估算） | 适用场景 |
| --- | --- | --- | --- | --- | --- |
| ~1B | `gemma2:2b`、`phi3.5:mini`（约 1.5–3.8B） | 4-bit | ~0.7–1.5 GB | 宽裕 | 分类、抽取、极简问答；**质量有限** |
| ~3B | **`qwen2.5:3b`（中文较好，候选）**、`llama3.2:3b`、`gemma2:2b` | 4-bit | ~2 GB | **宽裕**（推荐起点） | NL→结构化、单轮问答、RAG 生成、目录卡片检索 |
| ~7–8B | **`qwen2.5:7b`（中文较好，候选）**、`mistral:7b`、`llama3.1:8b` | 4-bit | ~4.5–5 GB | **紧张**（贴近上限；上下文要小） | 更高质量 RAG 生成/多轮；**需实测** |
| 13–14B | — | 4-bit | ~8 GB | **不可行** | （需更大内存机器） |
| Embedding（**多语言，P1-1**） | `bge-m3`、`multilingual-e5-*`、`qwen3-embedding` 等候选 | — | 约 0.3–1 GB（估算） | 宽裕 | RAG 检索向量化；**必须先测中文检索** |

> **候选 ≠ 裁定（P2-19）**：上表模型名只是 `ollama pull` 的**起点候选**（便于执行 §8）；**是否可用、实际体积、中文/英文表现均以本机实测为准**（`ollama list` / `du -sh` / Option B 的 golden set）。**不得**把"`qwen2.5:3b` 中文较好"当作已核实事实——它需要实测。

> **选择原则**：先用 **3B** 跑通链路并把评测基线建起来；再试 7B/8B 看质量提升是否值得"内存吃紧 + 延迟变高"；**不要**一上来就用最大模型。
> **中文能力**：不同模型的中文表现差异大，**必须实测**（本路线图的目标语料是中文技术文档问答）；**embedding 的中文检索能力同样必须实测且优先级更高**（头号风险，P1-1）。
> **决策依据**：以 Option B 的 golden set 指标（**目录检索命中率、文档检索命中率、引用正确性**、NL→JSON 合规率、延迟）为准，而不是"感觉更好"。

### 4.2 磁盘与下载成本提示（22 GiB 硬约束）

| 项目 | 估算占用 | 备注 |
| --- | --- | --- |
| chat 模型（3B 4-bit） | ~2 GB | 最小可行 |
| chat 模型（7B/8B 4-bit） | ~4.5–5 GB | 若保留多个会很快吃满 |
| embedding 模型（**多语言**） | 约 0.3–1 GB | 候选见 §4.1；维度/体积待实测 |
| 模型缓存/临时文件 | 与模型同量级（下载/转换时可能翻倍） | **下载时需预留 2× 空间**（估算） |
| Docker 镜像（mysql/app/向量库） | 数 GB（向量库另计） | Option C 的主要压力 |
| 构建产物（`target/`、`node_modules`、`frontend/dist`） | 数 GB | 已有；清理可释放 |

**一次性总账示例（P2-20）**：3B chat ≈ **2 GB** + 多语言 embedding ≈ **0.3 GB** + 下载/转换临时空间 ≈ **2×** → 单次安装**峰值 ≈ 5 GB**；再加上**既有** Docker 镜像与构建产物（数 GB）→ 在 **22 GiB** 可用磁盘下**可安全保留 1 个 chat 模型 + 1 个 embedding 模型**（但**不要**同时保留 3B 与 7B）。

**建议**：① 只保留**当前使用**的模型，测完即删；② 下载前用 `df -h /` 复核可用空间；③ 若需要多个模型对比，用**外部盘**（须用户决定）或逐个替换。

## 6. 本地 vs 外部 API 的决策树

```
需要 LLM 能力
├─ 是否必须在离线/隐私敏感环境下运行？
│   ├─ 是 → 本地（本机原生 Ollama）
│   └─ 否 ↓
├─ 任务质量要求是否超过 3B–8B 4-bit 的能力上限？
│   ├─ 是 → 外部 API（或更大内存机器/云 GPU）
│   └─ 否 ↓
├─ 单请求延迟是否可接受（本地推理更慢）？
│   ├─ 否 → 外部 API（或更小模型/更短输出）
│   └─ 是 ↓
├─ 是否愿意承担 token 成本与数据出境？
│   ├─ 否 → 本地
│   └─ 是 → 可本地为主 + 外部兜底（显式开关）
└─ 结论：默认本地；外部 API 只作为**显式开关的兜底**（需用户批准 token 政策）
```

| 场景 | 建议 |
| --- | --- |
| 演示/作品集（离线、零成本） | **本地** |
| 中文技术文档 RAG + 电影目录语义检索（语料受控） | **本地**，模型与 embedding 选型依据 golden set（**embedding 必须多语言并先实测**） |
| 不想受 8 GiB 限制 / 要最高质量与最低延迟 | **外部 API**（即总览的 **Option B-API**；同一套 Spring AI 代码，代价是 token 计费与数据出境） |
| 需要长上下文/复杂推理 | 外部 API 或更大机器 |
| 夜间评测大批量跑 | 视成本决定；本地"免费但慢" |
| 写操作 agent（Option C） | 模型只做"提议"，安全性由服务端保证 → **本地即可**（不依赖模型可信度） |

## 7. 部署形态对比

| 形态 | 可行性 | 成本维度 | 备注 |
| --- | --- | --- | --- |
| **本机原生（Ollama / llama.cpp）** | ✅ **推荐** | 一次性（电费/时间）；无 token | 唯一能在现有硬件跑通的形态 |
| **Docker 容器内** | ❌ **不可行（本机）** | — | ① Docker Desktop 仅 3.826 GiB（`docker info`；**虽可调大，但会挤压宿主 8 GiB**）；② **macOS 上容器无法访问 Apple GPU（无 Metal 直通）→ 容器内 Ollama 只能 CPU 推理、比原生慢一个量级**（P1-4） |
| **局域网大内存机器**（如 32/64 GiB Mac/PC） | ⚠️ 需设备 | 设备成本 + 运维；无 token | 需用户确认是否有机器；接入方式 = 指向该机器的 `base-url`（**须注意网络暴露与认证**） |
| **云 GPU** | ⚠️ 可行但有成本 | 按小时计费（或自建） | 与"避免 token 成本"目标部分冲突（但单位成本可控）；需网络与数据出境评估 |
| **外部 LLM API** | ✅ 可行 | 按 token | 质量最高、成本随用量增长；作为**兜底开关** |
| **混合：本地默认 + 外部兜底** | ✅ 推荐 | 以本地为主 | 与用户目标最兼容，需用户批准外部 token 政策 |

**关于 Docker 方案的可行性边界（P1-4/P2-21）**：若坚持容器化，**换 32/64 GiB 内存的机器后容器化才可能可行**（内存足够同时跑 MySQL + app + Ollama）；在本机只是"调大 Docker Desktop 内存配额"则几乎必然触发换页（宿主 8 GiB 被挤压），**不建议**。**即使内存够，macOS 容器也拿不到 GPU**——容器内 Ollama 只能 CPU 推理，比原生慢一个量级；在 macOS 上只要想用 Metal，就必须在**原生进程**里跑 Ollama。

## 9. 风险与回退

| 风险 | 影响 | 缓解 / 回退 |
| --- | --- | --- |
| 3.8 GiB Docker 内存导致"以为能容器化" | 方案失败 | 明确**原生运行**；不把 Ollama 放进 Compose（除非**内存≥ 32/64 GiB** 的机器）；另：**macOS 容器无 GPU 直通**，容器化会让推理慢一个量级（P1-4） |
| 磁盘 22 GiB 不够 | 无法下载/更新模型 | 一次只保留一个 chat 模型；下载前预留 2×；清理构建产物 |
| 8 GiB 触发换页/降频 | 延迟高、体验差 | 3B 起步；限制 `num_ctx` 与输出长度；并发 = 1；实测后定稿 |
| 模型中文能力不足 | RAG 质量差 | 用 golden set 选型；必要时换模型或外部 API |
| 模型/版本变更导致评测不可比 | 无法判断改进 | **固定并记录模型版本**；评测报告带模型指纹 |
| 应用启动时模型未运行 | 端点失败 | 明确失败语义 + 前端提示；可选"启动检查/重试"（待设计） |
| 学到的参数与本机不符（网上"经验值"） | 误导 | **只采信本机实测**；本文所有估算需实测替换 |
| 供应链/许可风险（模型许可，P2-22） | 合规 | 只用许可明确允许使用的模型；**逐模型核对许可**（Llama = Meta Llama Community License；Gemma = Gemma Terms of Use；Qwen 多为 Apache-2.0；Mistral 7B = Apache-2.0；Phi = MIT——**均以模型页为准，实施时逐条确认**）；记录模型来源与许可（已同步进总览 §8 安全/合规表） |

**回退**：① 停用 AI 开关（应用回到无 AI 状态）；② 卸载/停用推理进程；③ 若本地不可行 → 外部 API 兜底（需批准）。
